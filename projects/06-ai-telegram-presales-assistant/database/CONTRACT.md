# Phase06 database runtime contract

Apply original migrations 001 and 002, then `003_runtime.sql`. All runtime functions are SECURITY INVOKER. Use parameterized calls and explicit `::jsonb`, `::bigint`, and `::uuid` casts. Handoff tickets always enter the local queue; owner notifications are queued only after an operator configures the private owner chat.

## Ingestion and decision worker

- `presales.accept_update(p jsonb) -> jsonb`: accepts a raw Telegram Update or the parent's flat `{update_id,message_id,chat_id,user_id,username,display_name,text,message_type,timestamp}` envelope. Raw updates validate private chat and non-bot sender; flat envelopes must come from the trusted workflow's private-human validation (optional `chat_type`/`is_bot` are honored). Private sender/chat IDs must match. Unsupported, overlong and sensitive human messages are accepted with safe placeholders and `message_type=unsupported|too_long|sensitive`, so the engine can issue a deterministic response. Returns `status: accepted|duplicate|ignored`, plus available `update_id,conversation_id,customer_id,message_id`. Returned `message_id` is the database UUID; `telegram_message_id` is the Telegram integer. Invalid identities/shapes are ignored. No raw update is retained.
- `presales.claim_inbox() -> jsonb|null`: atomically claims the oldest unfinished message of an available conversation for **600 seconds**. Returns `{update_id,lease_token,lease_until,attempts,conversation_id,customer_id,message_id,conversation_status,envelope:{text,message_type,chat_id,user_id,telegram_message_id,update_id,sent_at,username,display_name},state:{requirements,consent,contact_present,...},catalog:{services:[],packages:[],adjustments:[],policies:[],faqs:[]}}`. `contact_present` is derived from the customer record and current consent; no raw email is returned. Catalog rows must be active and approved. A dead-letter inbox entry blocks later messages in its conversation pending manual replay. Suppress automatic estimates when `conversation_status=handed_off`; the database also rejects them.
- `presales.commit_decision(p_update_id bigint,p_lease_token uuid,p_decision jsonb) -> jsonb`: decision is `{state,consent_status?,consent_evidence?:object,response:string,estimate?:{service_code? OR package_code?,total_min,total_max,calculation,disclaimer},lead?:{score,status,reasons,summary,approved?:boolean},handoff?:{reason,priority,summary},reset?:boolean,privacy_delete_requested?:boolean,event_type}`. An estimate requires exactly one approved active service or package; service estimates support narrow `crm_data_entry` scope. State must be an object, response a nonempty string of at most 4096 characters. Updates state/consent and optional records, appends consent evidence when supplied, writes one audit event, inserts exactly one customer reply and optionally one `owner_notify`, and completes inbox in one transaction. Returns `{status:completed|duplicate,update_id,outbox_id,owner_outbox_id,...}`. Repeating a successful commit with its original token returns duplicate; other stale/expired tokens raise SQLSTATE 55000. A two-argument `(p_update_id bigint,p_decision jsonb)` wrapper accepts `p_decision.lease_token`. An unapproved score persists with `status=unqualified,score_approved=false`; set `lead.approved=true` only after the explicit user approval handled by the parent workflow.
- `presales.fail_inbox(p_update_id bigint,p_lease_token uuid,p_error text,p_retryable boolean DEFAULT true) -> jsonb`: token-fenced failure, exponential retry (5,10,20,40 seconds), dead letter at five attempts or immediately if nonretryable. Expired inbox leases can be reclaimed with a fresh token. No lease extension: finish within 600 seconds.
- `presales.replay_inbox(p_update_id bigint) -> jsonb`: manually retries dead letters, resets attempts; completed entries are never replayed.

## Telegram delivery worker

- `presales.claim_outbox() -> jsonb|null`: returns `{id,outbox_id,lease_token,lease_until,attempts,update_id,job_type,payload:{chat_id,text}}` (`id=outbox_id`), leased for 120 seconds, ordered per destination chat. Runtime `telegram_reply` and `owner_notify` jobs share the same Telegram delivery/finish protocol. Customer replies should say the handoff was recorded, without claiming owner delivery.
- `presales.finish_outbox(p_outbox_id uuid,p_lease_token uuid,p_result jsonb) -> jsonb`: parent-compatible result `{ok,message_id,status,retry_after,error}`. `ok=true` requires a positive message ID. Numeric HTTP 429 retries with at least `retry_after` seconds, rounding fractional delays upward. Delays over one day, negative delays, or malformed supplied delays are quarantined as dead letters for operator review, never capped to an earlier retry. Numeric JSON values and decimal numeric strings are accepted. Missing/null delays use normal backoff. Other 4xx dead-letter; ambiguous/5xx/network failures become uncertain dead letters. Explicit string statuses `retry|dead_letter|unknown` are also supported. Five attempts maximum; token/lease fenced. Repeating successful acknowledgement with the same token/message ID returns duplicate.
- The five-argument overload `finish_outbox(uuid,uuid,p_outcome text,p_telegram_message_id bigint,p_error text)` accepts `sent|retry|dead_letter|unknown`; supply all five arguments, using explicit NULL where needed. Use `retry` only for confirmed nondelivery.
- `presales.replay_outbox(p_outbox_id uuid,p_acknowledge_possible_duplicate boolean DEFAULT false) -> jsonb`: manually retries dead letters. An uncertain delivery requires explicit `true`; inspect delivery first. Sent entries are never replayed.

Database replay cannot enqueue a second reply for one update. Telegram sendMessage has no idempotency key: exactly-once network delivery cannot be guaranteed after a crash or ambiguous response. Expired delivery leases become dead letters, never automatic retries; a dead letter blocks later replies in the conversation until manually resolved/replayed. Persist Telegram success immediately through finish_outbox.

## State, privacy, approval

Fresh state is `{requirements:{},consent:"unknown"}`. `reset:true` resets saved working state to that baseline while retaining the customer's existing consent; an explicit `consent_status` overrides it. Otherwise `state` replaces working state and the canonical customer's consent always populates `state.consent`. Optional null estimate/lead/handoff values mean absent. Privacy deletion requests record a local audit request and human handoff for review; they do not silently erase history or mark deletion completed.

On the next new message, sessions idle over 24 hours expire only when no unfinished inbox jobs remain. A fresh conversation is created without deleting historical messages/state. Repeated handoffs reuse an existing active ticket; owner notifications are generated only for a new ticket or changed reason.

Lead writes require granted consent and a stored contact; otherwise the optional lead is omitted (`lead_id=null`). Eligible but unapproved scores remain unqualified. Estimates require the exact active, approved `estimate_disclaimer.policy_value.text` and an approved ceiling policy. Above-ceiling estimates or services marked `requires_human` require a handoff and are saved as `human_review`. All totals must be numeric with valid nonnegative ranges. The parent deterministic engine remains responsible for calculating totals and adjustment line items; SQL does not independently recalculate arbitrary `calculation` JSON.

Obvious credential text, common credential formats, unsolicited email addresses and long phone-like digit strings are redacted before persistence; JSON credential keys are recursively redacted. This is defense in depth, not a complete secret/PII detector. Only an exact `/contact person@example.com` message received after stored consent is granted saves the user-provided email in `customers.contact_email`; the worker receives `/contact [EMAIL STORED WITH CONSENT]`. The command cannot independently prove email ownership. Consent denial/withdrawal clears that contact field. `consent_events` appends the canonical source message, prior/new status, redacted text and optional decision evidence. Historical rows are preserved, legacy chat IDs are backfilled from private customers' Telegram IDs, and the most recent nonclosed conversation is reused. Legacy duplicate chat/message rows are retained behind a unique canonical receipt.

New catalog `approved` flags default false; existing migration-002 catalog rows are marked approved once on migration, consistent with its approved-catalog designation. Future catalog changes must explicitly manage approval.

`runtime_settings(key,value jsonb)` is private configuration and never appears in worker state or catalog. Operator-only `presales.configure_owner_chat(p_chat_id bigint)` sets `owner_chat_id` as a JSON number. The parent may instead configure it with `INSERT ... SELECT` from the sole existing test customer; never put the live ID in source files. An owner notification includes ticket/conversation IDs, reason, priority and summary, and contact only if consent is granted at commit time. No configured target means local ticket only. No real chat target is seeded by this migration.

Runtime functions and new tables are not granted to PUBLIC. Deployment must grant a trusted worker role schema usage, function execution and required table privileges because functions use invoker rights. Such a role can bypass function fences with direct SQL; keep it trusted and inaccessible to Telegram users. Replay access is an operator responsibility.

## Verification

`tests/run_rollback_tests.sh` reads original 001/002 from WSL, loads `tests/002_legacy_fixture.sql` **before** 003, applies 003 twice, then runs `tests/003_runtime_assertions.sql` in a unique schema inside one transaction ending ROLLBACK. It uses the already-running Postgres container's configured connection identity without reading `.env` or printing credentials. The assertion file expects that synthetic legacy fixture; it must not be run standalone against live data. No Telegram messages are sent. Tests cover preservation, migration reruns, deduplication, token fencing, retry/dead-letter/replay, atomic rollback, consent/contact/approval, handoff reuse, catalog filtering and owner queueing.

`tests/run_concurrent_integration.py` is a separate Python-standard-library test run from WSL. It is hard-locked to existing disposable database `p06_verify_20261014` in the already-running `project06-presales-postgres-1` container. Run `python3 /path/to/implementation/database/tests/run_concurrent_integration.py --apply-migration` to explicitly apply the current staging 003 there first; omit the flag when already applied. It refuses unfinished pre-existing inbox/outbox jobs, and each claim rolls back if it accidentally encounters another run's job. Coordinate use of this disposable database while the test is running.

The concurrency suite uses independent psql connections with synchronized starts: 16 identical-update ingests, 16 alternate-update same-message ingests, three chats with three messages each, 16 simultaneous claimers, and four simultaneous commits/acknowledgements per job. Assertions check exactly one message/inbox/reply per update, serial leases, committed-state visibility, per-chat reply order, and replay audit deduplication. Seven additional rollback scenarios check ordinary, fractional, one-day, over-one-day, huge numeric and invalid retry delays. A final cleanup removes only this run's randomly identified, explicitly marked synthetic rows and compares hashes/counts of all 22 pre-existing tables. Sequences advance normally; they are not reset. This script does not truncate/drop schemas, change container lifecycle, read `.env`, call Telegram, or connect to the live database. The optional migration remains applied to the disposable database.
